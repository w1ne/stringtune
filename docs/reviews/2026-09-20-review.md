# StringTune code and design review — 2026-09-20

Reviewed master b96b151e61bcc9d87a8de0bebc0759f07514df08 and https://stringtune.com in headless Chrome. No production changes made.

## Confirmed findings

1. **High: microphone failure has no retry.** On the live page, inject a rejected getUserMedia promise, click Start, dismiss the error: the start button stays hidden. application.js calls async init without awaiting it; tuner.js swallows both engine and permission errors. Await startup through microphone and engine readiness, keep failures recoverable, clean up audio resources.
2. **High: manual reference tone crashes before mic startup.** Uncheck Auto and click a note on a fresh page. Chrome throws `Cannot read properties of undefined (reading 'createOscillator')`. Tuner.play assumes an existing AudioContext. Reference playback must initialize/resume its audio context independently of microphone permission.
3. **Medium: instrument selection has no functional effect.** Bass selection leaves all 96 chromatic notes unchanged. application.js only logs and sends analytics. Wire presets to visible string targets/reference tones while preserving chromatic detection.
4. **Medium: mobile horizontal overflow.** At 390px viewport, document scrollWidth is 495px. The 400px meter rotated through ±45 degrees and oversized note strip need responsive containment/geometry. Screenshot: /tmp/stringtune-review/mobile.png.
5. **Medium: invalid calibration persists.** initA4 accepts negative stored numbers; the dialog only checks parseInt truthiness. A4=-440 makes note math NaN. Validate finite numeric calibration within a documented supported range on both entry and read; provide recovery to 440.
6. **Medium: idle display implies a measurement.** Application constructor seeds A4=440 and the CSS needle starts at 45 degrees. Meter's renderer skips its zero-motion initial state. Show an idle placeholder and neutral needle until a valid signal arrives; distinguish silence from an in-tune reading.
7. **Medium: pitch accuracy needs investigation.** The actual checked-in WASM and worklet were driven with one second of 0.2-amplitude sine audio in 128-sample blocks at 44100/48000 Hz. Mean of final ten low-E bass readings is approximately +9.0/+6.4 cents. All 26 note/sample-rate combinations produced detections. These measurements cover synthetic tones, not real instruments or microphone capture. Results: dsp.json. Do not infer a detector rewrite is required until the bias is traced.
8. **High maintenance risk: tests do not protect runtime.** Nested npm ci fails because package.json requests Jest 29 but its lockfile contains Jest 30. cargo test --locked fails to compile unit tests calling an obsolete detector.detect(&signal) pointer API; implementation now returns bool and uses internal buffers. CI runs markdown/build/accessibility work but neither tuner Jest nor Rust tests. JavaScript tests also contain stale clarity/stability assumptions and an unfinished processor mock.

## Recommended first repair design

Preserve the dark/pink visual identity and existing localized content. Keep one tuner surface with a large detected note, readable tuning direction, neutral idle state, responsive meter, instrument string targets, and reference playback. Model microphone lifecycle explicitly (idle, starting, listening, error) with retry and cleanup. Initialize reference audio independently. Validate calibration and show errors inline. Make controls keyboard accessible with explicit names. Repair dependency/test contracts and add regression checks for the actual failures above before changing detector behavior.

Alternative: reliability-only repairs leave misleading instrument/UI controls in place; a full redesign expands risk and scope before the basic tuning flow is dependable. The focused repair pass is recommended.
